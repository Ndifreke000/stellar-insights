# QA: SEP-6 deposit & withdraw (`/[locale]/sep6`) — #1813

Manual browser verification of the SEP-6 (non-interactive) deposit/withdraw flow, with
particular attention to whether the two lint-suppressed `useEffect` hooks are masking a
real staleness bug in anchor/info data.

Setup and reporting conventions: [README](README.md).

## What the code does

[`sep6/page.tsx`](../../frontend/src/app/%5Blocale%5D/sep6/page.tsx) holds all state
locally. There are three panels:

1. **Anchor & transfer server** — a preset dropdown plus a free-text transfer server URL.
   The effective server is `selectedAnchor?.transfer_server || customTransferServer.trim()`.
2. **Request** — a deposit/withdraw toggle rendering
   [`Sep6DepositForm`](../../frontend/src/components/Sep6DepositForm.tsx) or
   [`Sep6WithdrawForm`](../../frontend/src/components/Sep6WithdrawForm.tsx), gated on
   `info` having loaded. Plus an optional JWT field.
3. **Transaction status** — lookup by id, and a manually refreshed recent-transactions list.

### Network calls

Via [`services/sep6.ts`](../../frontend/src/services/sep6.ts) →
[`fetchWithRetry`](../../frontend/src/services/fetchWithRetry.ts), prefixed with
`NEXT_PUBLIC_API_URL`:

| Trigger | Request |
| --- | --- |
| Mount, and "Refresh" | `GET /api/sep6/anchors` |
| Transfer server set | `GET /api/sep6/info?...` |
| Deposit submit | `GET /api/sep6/deposit?...` |
| Withdraw submit | `GET /api/sep6/withdraw?...` |
| Transactions "Refresh" | `GET /api/sep6/transactions?...` |
| Lookup by id | `GET /api/sep6/transaction?...` |

One retry on 503 honoring `Retry-After` (capped 5s); otherwise a `Sep6Error` carrying the
response `message` / `error`, else `statusText`.

## Blockers found by code read

### B1 — there is no SEP-6 backend

[`backend/src/api/`](../../backend/src/api/) contains `sep24_proxy.rs` and `sep31_proxy.rs`
but **no SEP-6 proxy module**. The only occurrences of "sep6" in the backend source are an
achievement definition in
[`backend/src/api/achievements.rs`](../../backend/src/api/achievements.rs) that matches on
the `/sep6` frontend path. Every `/api/sep6/*` call the page makes has no handler.

```bash
curl -i localhost:8080/api/sep6/anchors
```

Expect 404. This blocks essentially the whole plan: without `/anchors` and `/info`, the
Request panel never renders a form (it is gated on `info` being non-null), so deposit,
withdraw, and transaction lookup are all unreachable.

The first observable symptom is the red banner at the bottom of the page — text drawn from
the 404, or the fallback "Failed to load anchors. Is the backend proxy running?" if the
error is not an `Error` instance. Note which one you actually get; the fallback string
happens to be the useful one, and a bare "Not Found" is worth its own bug.

## The `useEffect` question from the issue

The issue asks whether the two hooks flagged for missing `loadAnchors` / `loadInfo`
dependencies are hiding a bug where anchor/info data goes stale after the initial load.

The hooks, at [page.tsx:148–155](../../frontend/src/app/%5Blocale%5D/sep6/page.tsx#L148):

```ts
useEffect(() => { loadAnchors(); }, []);
useEffect(() => { if (transferServer) loadInfo(); else setInfo(null); }, [transferServer]);
```

Reading the code, neither looks like it produces stale data in practice:

- **`loadAnchors`** is a `useCallback` over `[selectedAnchor]`. The mount effect captures
  the mount-time closure, where `selectedAnchor` is `null` — which is exactly the state the
  auto-select branch (`if (res.anchors?.length && !selectedAnchor)`) wants. Later refreshes
  go through the "Refresh" button, which calls the current closure. Adding the dependency
  would make the effect re-run on every anchor selection, which is worse.
- **`loadInfo`** is a `useCallback` over `[transferServer]`. The effect's dependency array
  is also `[transferServer]`, so the effect and the callback are recreated in the same
  render — the effect always calls the fresh closure.

So the lint suppressions look benign. **That is a code-reading conclusion, not a verified
one** — confirm it by driving the transitions in step 3, which is where a stale closure
would actually show up.

Separately, there are two transitions where data genuinely is *not* refetched, and those
are worth checking as real behavior rather than lint artifacts:

- Changing the **JWT** does not refetch `info` or transactions. Whether that matters
  depends on whether the anchor's `/info` varies by authentication.
- Toggling **deposit ↔ withdraw** does not refetch `info` — by design, since one `/info`
  response carries both maps. Confirm the forms actually re-derive their asset lists from
  it on toggle.

## Test steps

### 1. Page loads

1. Navigate to `/en/sep6` with Console and Network open.
2. Header, all three panels, and the deposit/withdraw toggle render.
3. `GET /api/sep6/anchors` fires exactly once on mount — not twice. (React 18 strict mode
   in dev double-invokes effects; if you see two, confirm against a production build before
   filing.)

**Expected (blocker):** 404 per B1, error banner at the bottom of the page.

### 2. Anchor selection

1. The preset dropdown populates from the response; "Select an anchor" is the placeholder.
2. Selecting an anchor triggers `GET /api/sep6/info` for that anchor's transfer server.
3. "Loading anchor capabilities…" appears while in flight, then resolves.
4. Click "Refresh". Confirm anchors reload and your current selection is **not** silently
   replaced by `anchors[0]`.

### 3. Staleness probe — the core of this issue

Drive these transitions in order, checking the Network tab after each. Every one should
fire a fresh `/api/sep6/info` for the *new* server, and the Request panel should reflect
the *new* response.

1. Select anchor A → note the asset codes offered in the deposit form.
2. Select anchor B (different transfer server) → a new `/info` fires; the asset codes
   change to B's. **Assets from A must not persist.**
3. Switch back to anchor A → `/info` fires again; A's assets return.
4. Type a custom transfer server URL into the free-text field (this clears the preset
   selection) → `/info` fires for the typed URL; assets update.
5. Clear the custom field with no preset selected → `info` is cleared; the Request panel
   drops back to its empty state and no stale form remains.
6. Toggle deposit ↔ withdraw at each of the above → the form's asset list and (for
   withdraw) the type list come from the current `info`, with no leftovers.

Any case where the form still shows the previous anchor's assets is the bug the issue
suspected. Capture the anchor pair, the order of actions, and both `/info` responses.

### 4. Deposit

1. With `info` loaded, select the deposit tab.
2. Fill the required fields; submit.
3. `GET /api/sep6/deposit` fires with asset code, account, and any extra fields.
4. The response renders as usable instructions — a `how` string, deposit address, memo,
   whatever the anchor returns — not a JSON blob and not `[object Object]`.

### 5. Withdraw

1. Select the withdraw tab.
2. Confirm the withdraw type list comes from `info.withdraw`; note the code falls back to a
   hard-coded `"bank_account"` when the anchor advertises none — check that fallback does
   not appear alongside real types.
3. Submit; `GET /api/sep6/withdraw` fires; the response renders readably.

### 6. Transaction status

1. Paste a known transaction id and click "Fetch". `GET /api/sep6/transaction` fires.
2. Status text, icon, and colour match the returned status — check `completed`, `pending`,
   and `error` if you can produce them. The matching is substring-based
   (`includes("complete")`, `includes("pending")`, …), so an unrecognised status falls
   through to a neutral clock icon rather than breaking.
3. Click "Refresh" on the recent list. `GET /api/sep6/transactions` fires with the current
   `kind` (deposit or withdraw) and `limit=20`.
4. Toggle deposit/withdraw and refresh again — the `kind` parameter must follow the toggle.
5. With no results, the empty state reads "No transactions loaded. Use JWT for
   authenticated anchors."
6. Enter a JWT and refresh. Confirm the JWT is sent in a **body or header, not a query
   string** — check the request URL in the Network tab. A JWT in a URL is a finding in its
   own right.

### 7. Error states

| Case | How to produce | Expect |
| --- | --- | --- |
| Bad transfer server | Type a URL that is not an anchor | Readable banner; no stale `info` left rendered |
| Unknown transaction id | Fetch a made-up id | "Transaction not found" or the anchor's message; no crash |
| Missing JWT on an authed anchor | Refresh transactions without a JWT | 401 surfaced as readable text naming the auth requirement |
| 503 | Force a 503 from the backend | Exactly two attempts ~1s apart, then a readable error |

The page has a single shared `error` state, so a new action clears the previous message.
Confirm an old error does not linger next to fresh successful data.

### 8. Console and network audit

- Zero console errors and zero unhandled rejections.
- No secrets in query strings.
- Layout holds at ~375px — the anchor row uses `min-w-[200px]` inside a flex-wrap.
